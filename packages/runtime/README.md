# @draflow/runtime

Use `MemoryRuntime` on a trusted host to publish and activate workflows. Each publication has its own revision and stores the resolved implementation version in each node's `typeVersion`. Editing or publishing a draft leaves the active revision serving events until activation succeeds.

```ts
const runtime = new MemoryRuntime({ registry });
runtime.saveDraft(workflow);
const publication = runtime.publish(workflow.id);
await runtime.activate(workflow.id, publication.revision);
const execution = await runtime.fire(workflow.id, triggerNodeId, {
  items: [{ json: { orderId: 42 } }],
  key: 'order-created-42',
});
```

The returned execution identifies the source node, event key (if supplied), workflow, revision, resolved node versions and engine result. The host can supply a run ID or use the one generated by the engine. Event keys are metadata in this memory implementation. Store the returned record if you need history.

For push sources, supply a `registerTrigger` adapter. The runtime calls it for each enabled trigger-category node with a revision-specific `fire` callback. Attach cleanup to the supplied abort signal before allocating resources. A registration must support staging alongside the old revision. Its callback rejects while staged and after removal. A failed registration aborts the candidate's signal, leaving the old callbacks live. Deactivation closes intake and lets accepted runs finish.

To rehydrate a saved publication, call `restore(publication)` and then `activate(id, revision)`. Restore checks that each pinned node version is installed before making the publication available for activation.
