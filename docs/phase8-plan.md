# Phase 8 提案　Proodに組み込むプロジェクト自動化

## 判断と分担

対象はDraflow main `6283174`（Phase 7.4まで）とProod main `ed2c60c`（PR #6まで）。Proodの並行開発ブランチは前提に含めない。以下は設計・受け入れ条件の提案である。

最初のリリース例は「このプロジェクトでタスクが『レビュー待ち』に変わり、担当者が空なら、レビュー担当者を設定する」。利用者が作成時に読んだ一文から、発火・不発火の理由、誰の権限で何を変えたか、障害後にもう一度実行してよいかまで説明できることを出荷基準にする。

| 観点 | 現在利用できるもの | 利用者に届くまでの不足 |
| --- | --- | --- |
| トリガー | Draflowの手動・Webhook・スケジュール受付、版固定。Proodのタスク作成・更新と同一トランザクションのOutbox | 明示的な状態遷移、意味のある変更だけの抽出、配送・購読の再開、自己発火防止 |
| 許可アクション | ノード登録、公開時検証、HTTP資格情報の宛先制限。Proodの共通タスク操作 | プロジェクトごとの許可操作、型付き入力と選択肢、子フロー・インポートも含む公開制限 |
| 実行主体 | Draflowの組織別管理権限・操作監査。Proodのワークスペース／プロジェクト実効権限と親からの可視性継承 | ルール管理者、起点となった人、実際に業務を書き換える人の区別と、実行時の再認可 |
| 再試行・副作用 | 永続待機、失敗位置からの再実行、キー付き配送、結果不明の照合、明示的な補償 | Prood側の操作受領記録、手動編集との競合判定、タスク単位の説明と安全な再操作 |

Draflowはホスト提供のイベント・アクション定義、版、実行文脈、受付・副作用キー、試行履歴を扱う。Proodは業務イベント、候補の可視範囲、権限、タスクの更新・監査を所有する。Web・MCP・Automationは同じアプリケーション操作を使う。Draflow組織とProodワークスペースの対応を明示し、プロジェクトや継承されたサブタスクの認可はProodで評価する。[Draflowの実行・復旧](../apps/server/README.md)・[Proodの分担](../../Prood_Docs/docs/new-atlas-design.md)・[Proodのタスク操作](https://github.com/TommyKammy/Prood/blob/ed2c60c/packages/application/src/work.ts)・[Outbox契約](https://github.com/TommyKammy/Prood/blob/ed2c60c/packages/application/src/persistence.ts)

## 8.1　P0　業務トリガーと確実な受付

最初に発火の意味を固定する。ProodのOutboxにはイベントID、成否、主体、配送状態・期限などの列があるが、リポジトリ契約は追加・一覧が中心。更新イベントの changes はパッチ指定項目の更新後の値で、実際の遷移を表す契約ではない。購読対象フィールドだけの変更前後、対象の単調増加版、原因イベント／ルール実行IDを追加し、既存の監査イベントと互換にする。手動開始には対象タスクの指定と開始者の権限が必要。定期起動は既存のスケジューラを再利用し、期限変更・取消に追従する「期限前日」は後続候補とする。

- タスク作成、状態A→B、未割当→担当者ありをWeb・MCPの双方から確認する。同値保存、説明のみ変更、拒否・ロールバックで状態変更トリガーの実行は0件。旧版イベントから変更前を推測せず、対応する購読だけに配送する。
- Proodでリース付き取得・再取得・確認を実装する。Draflowの永続受付後に確認を返す。2購読の一方だけを受け付けて停止し、再送・再起動・ルール改訂を挟んでも、対象イベント×ルールごとに選定済みの版で1実行。通常のWebhook重複排除期限を超える再配送でも同じ結果になるよう、保持期間または永続購読記録を設計する。
- 同一タスクの遅延・逆順配送で古いイベントが新状態を巻き戻さない。A→A、A→B→Aの連鎖は原因を記録して打ち切り、無関係な次の手動更新は通常どおり発火する。ワークスペースを越える配送は0件。

## 8.2　P0　許可アクションと実行主体

初版は「担当者を設定」「状態を変更」を推奨する。既存のタスク更新を利用でき、結果をタスク画面で検証できる。設定は固定IDまたは許可されたイベント項目の参照。ルールごとに名前付きの実行主体と対象プロジェクトを明示する。初期値は有効化した利用者からの明示的な委任。無人の共有サービス主体は別途、任命・範囲制限・失効・監査を整えた段階で追加する。

- 公開前に「いつ／条件／何を／誰の権限で」を表示。公開・停止・委任変更はProodのプロジェクト管理権限で判定し、実行主体の交代には新しい委任が必要。イベント発行者やDraflowの組織管理者の権限への自動切替は行わない。
- サーバーは定義の版・全経路・子フローを検査し、任意HTTP、任意URL、未許可ノード・操作、他プロジェクトの状態や非表示の候補を拒否する。同じ文書をUI・API・インポートから渡しても結果が一致する。
- 実行・待機復帰・再試行の各書込み直前にProodが有効な委任、現在の実効権限、対象の実効プロジェクト、アクションの入力を検証する。非公開プロジェクト、別組織、親から可視性を継承したサブタスク、公開後の降格・脱退・対象者失効を試し、不許可時の変更・外部送信は0件。監査では起点の人・設定者・実行主体・ルール版を区別し、利用者に見えない対象名を表示しない。

## 8.3　P0　副作用の受領記録と再試行

Draflowの重複排除に加え、実際にタスクを書き換えるProodが操作キーを受け取り、業務更新、結果の受領記録、派生Outboxイベントを一緒にコミットする。キーは試行番号と独立させ、ルール実行・アクション・対象ごとに固定する。初版の自動書込みはこの段階の通過後に有効化する。

- DBコミットの直前／直後、応答前、Draflowの結果保存前でそれぞれ停止させる。同時二重要求や再起動後の再試行でも実更新1件、受領結果1件、派生イベント1件。同じキー・異なる入力は競合。同じキー・確定済み操作は現在の閲覧権限を確認して記録済み結果を返し、書き直さない。
- 「担当者が空なら設定」の実行前に人が担当者を決めた場合は条件不成立として終了する。実行直後に人が担当者を直し、元の応答だけが失われた場合も、その編集を維持する。期待版や期待フィールドを業務更新と原子的に照合する。
- 一時障害は上限付き再試行、権限失効は停止、条件不成立はスキップ、外部で適用済みか不明なら要確認。結果照会・冪等キーのないメール等は自動再送の対象外。取消後の未着手操作は0件。補償は定義済み逆操作だけを現在権限・状態で実行し、後続の人手編集は維持する。
- SQLite・PostgreSQLの両方で上記を確認する。既存のWebhook、スケジュール、HTTP配送、再実行・補償の回帰、および旧ワークフローの読込・実行を継続する。

## 8.4　P1・一般提供の条件　ルール作成、試運転、業務履歴

プロジェクト画面でテンプレートから「いつ／もし／実行する」を選び、対象・権限・結果を読めるようにする。ホスト提供の表示名、選択器、説明を使い、翻訳はProodの辞書に置く。詳細な技術調査はPhase 7の運用画面に接続する。

- プロジェクト管理者がテンプレートから冒頭のルールを作り、実データの閲覧権限内でサンプルを選び、公開・一時停止できる。試運転は同じ条件・入力解決・認可を通し、対象、変更前後、スキップ理由を示す。業務更新、実通知、実行待ち登録は0件。
- タスクから「この更新の理由」、ルールから「動かなかった理由」を追える。人手・Automationの区別、版、実行主体、既に適用した操作、次に許される操作を表示する。閲覧者は再操作できず、二人が別タブから逆の照合判断を行っても1件だけが確定する。
- キーボードだけで作成→試運転→公開→履歴確認を完了する。Automationを開かない利用者の共通シェルにエディタやランタイムを含めない。現行シェルgzip、タスク更新p95、Outbox滞留から受付までのp95を同一データ・同一環境で比較し、同期リクエストはDraflowの応答を待たず完了する。

## その後の汎用化

ホストごとのコネクタ配布・互換性検査、進行中の長期実行を新しい定義へ移す手順、組織別クォータ・履歴保持、複数段承認、営業日・祝日を含む日程、監査の外部出力を後続候補とする。初版の利用データ（スキップ・競合・要確認件数、利用者が原因をたどれた割合）で順序を見直す。通知・SMTP、タスク作成、他プロジェクト更新は、誤送信、課題キー採番、権限横断それぞれの受け入れ試験を追加してからカタログを拡張する。
