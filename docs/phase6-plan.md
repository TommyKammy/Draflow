# Phase 6 計画案　定時同期と部分失敗からの復旧

評価基準は Phase 5 マージ後の main（7624479）。最初の利用例を「同じ受注の変更を定時に取り込み、外部への登録失敗を担当者が復旧する」と置いた。以下の件数・並列度・性能目標は試験用の提案値である。

## 現在の保証と不足

| 場面 | Phase 5 の保証 | Phase 6 で必要な判断 |
|---|---|---|
| 同じ通知が再送された | 受付キーによる重複排除があり、定時実行も発火時刻を記録する | 別時刻の実行で同じ業務変更が届いたとき、登録済みか、新しい版か |
| ページの途中で再起動した | SQLite が現在ページ、子の実行、成功バッチを結び、同じ run を再開する | 次の定時実行がどの変更位置から始まり、削除や遅着をどう扱うか |
| 外部登録の応答を失った | 記録付き HTTP は同じ実行位置のキーで再試行、または人手で照合できる | 終了済みの失敗を再実行しても、成功分を再送せず同一の業務操作として追跡できるか |
| 大きな同期を取り消した | 単一ワーカーがバッチ間で他のジョブに実行機会を渡し、取消が後続の開始を抑える | 複数の子が順不同に完了した場合の確定位置と、既に外部で成立した操作を取り消す手順 |

根拠は [SQLite の台帳と完了処理](../apps/server/src/sqlite.ts)、[ワーカー](../apps/server/src/host.ts)、[現行の運用契約](../apps/server/README.md)、[強制停止試験](../apps/server/test/composition-crash.test.mjs)。現在のページ位置と送信キーは実行に属する。終了時に破棄するチェックポイントや、保存を無効にできる閲覧履歴に再実行を依存させると、運用設定で復旧可能性が変わる。

## 6.1　P0　実行をまたぐ差分同期・重複排除

固定された同期元・対象範囲・宛先を識別する同期設定を導入する。初版は取得元が変更トークンと安定した変更 ID（または業務 ID と単調な版）を提供する場合を扱う。今回のページを続けるカーソルと、次回の同期開始トークンを区別する。同じ対象の実行が重なっても進行役は一つ。変更の適用記録と外部送信キーを実行をまたいで保持し、今回の変更が全件確定してから次回の位置を更新する。同期先やフィルターを変えた場合は明示的に初期化する。ページと次回同期のトークンを分ける実例は [Microsoft Graph の差分取得](https://learn.microsoft.com/en-us/graph/delta-query-overview) を参照。

**受け入れ条件**

- 初回100件の後、作成2件、別々の既存行の更新3件、削除1件を、重複通知2件・同一更新時刻を交えて配信する。第2回の有効な外部変更は6件、最終行数は101件、第3回の外部変更は0件。同一 ID の新しい版は適用し、後から届いた古い版で削除済み行を復活させない。
- 手動起動と定時起動の同時受付、受信先コミット直後の応答消失、同期位置の確定直前・直後の SIGKILL を試す。復旧後の宛先を基準データと全件照合し、取りこぼし・重複適用・位置の巻き戻りはいずれも0件。適用結果が不明なら位置を保持し、冪等性を提供しない宛先では照合を要求する。
- 空の中間ページと変更0件の終端を区別する。トークン失効時は要再同期とし、明示的な再同期後も既存行を二重登録しない。重複記録の保持期間は取得元の再配信期間と宛先の冪等性キー有効期間に合わせ、保証期間を越えた再配信は照合に回す。
- 更新時刻しか提供しない取得元は別の対応段階とする。採用条件は同時刻のタイブレーク、遅着の上限と重複取得期間、削除通知の契約が定義できること。

## 6.2　P0　失敗位置からの明示的な再実行

運用者が失敗した run の未完了部分を指定して再実行できるようにする。初版の対象はページ・バッチと記録付き送信。元の run と各試行を結び、公開版、入力、論理操作のキー、成功済みの結果を再利用する。保持期限内の再実行用データを閲覧履歴と独立に持ち、CLI に再実行可能な位置・理由・期限を表示する。同じ入力・定義で成功済み処理を引き継ぐ設計の参考は [AWS Step Functions の redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)。

**受け入れ条件**

- 100件を25件ずつ扱い、3番目のバッチの途中で確定的な失敗を発生させる。宛先復旧後に再実行し、先頭50件と3番目のバッチ内の成功済み明細への追加送信は0件。最終的な適用 ID は100件ちょうど。子 v2 の公開後も元の親・子の版を使う。
- 同じ再実行要求を二重送信し、受付直後に強制停止する。復旧後の追加試行は1件。元の失敗、追加試行、最終結果を相互に照会でき、詳細履歴を削除しても保持期限内は復旧できる。
- 結果不明の非冪等送信は自動で再送しない。照合で適用済みなら送信0回、未適用なら1回。入力や必要な記録の期限切れ、追跡不能な外部作用がある場合は理由を示して停止する。明示取消済みの run は通常の再実行操作で再開しない。

## 6.3　P1　同時数を制限した並列バッチ

独立した明細を扱い、実測で逐次処理が所要時間の目標を超える案件に導入する。初版は単一 Node ホスト・同一ページ内の I/O 並行実行。既定は1。子の受付・成功・失敗をバッチごとに保持し、全成功後にページを解放する。同じ業務 ID に順序制約がある場合は直列化する。外部への到着順を要求するフローは並列度1を選ぶ。

**受け入れ条件**

- 1,003件・41バッチを並列度1と4で処理する。意図的に後続を先に完了させ、途中の1バッチを失敗させても、そのページの次カーソルは未確定。再起動後は成功済みバッチを再送せず、復旧後の件数・集計・宛先の ID と版が逐次実行と一致する。
- 2つの同期が同時に進む試験で、実測した処理中の子数が同期別・ホスト全体の設定上限を守る。同じ ID の更新順を保ち、短い独立ジョブが大型同期の完了前に終了する。429 の共有待機中に同じ制限対象への新規送信は0件。取消と複数の子の完了を競合させ、確定分と照合対象がすべて残る。
- 各バッチの下流 I/O に一定の待ち時間を設け、同一環境で5回測定する。独立明細の試験では並列度4の完了時間中央値を逐次の60%以下とする案。ピークメモリ、DB サイズ、短いジョブの受付・待ち時間 p95 も記録する。10倍のページ数で復旧用の明細が現在ページと処理中バッチの範囲に収まることを確認する。

## 6.4　P1・案件依存　明示的な補償処理

複数サービスで成立した操作を業務上取り消す必要がある案件に導入する。成功した操作に、固定版の補償用サブワークフロー、対象 ID、条件、独立した冪等性キーを関連付ける。初版は順序が定まった処理列。運用者の明示要求または公開時に指定した失敗方針で開始し、通常の取消は Phase 5 の意味を維持する。作用を戻す順番と方法は業務が指定する。[Azure の補償トランザクション](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

**受け入れ条件**

- 「在庫予約成功 → 決済成功 → 配送作成失敗」で返金・予約解除を順に実行する。配送取消は0回。元の予約 ID と決済 ID を使い、その後に別利用者が行った更新を上書きしない。
- 返金受付直後・応答前に強制停止し、同じ補償要求を二重送信する。冪等な宛先での返金・解除は各1件。結果不明なら照合待ち、解除だけが失敗すれば解除だけを再試行する。照会では元の失敗、補償中、補償済み、要手動対応を区別できる。
- 同じ業務操作に対する再実行と補償を同時要求し、片方のみが進む。通常の取消で返金は発生しない。未確定の元操作は、適用されたと照合できてから補償対象にする。

## 共通の出荷判定

各段階で旧 SQLite の移行、従来の Wait・二重通知・記録付き HTTP・親子の取消競合・逐次バッチ・履歴再生を回帰試験する。Node.js 最小サポート版とブラウザで確認し、Phase 5 の main と同条件で gzip、短い処理の受付 p95、同期完了時間、ピーク RSS、台帳の保持量を比較する。差分同期の実用最小単位は 6.1 と 6.2。並列化は性能要件、補償は取消可能な外部 API と業務要件を出荷判断に使う。分散ワーカー・HA、複数組織の権限分離、運用者向け画面は別の導入要件として扱う。

## 6.1・6.2 の実装と検証結果

Node ホストの SQLite を使い、6.1 は `draflow.pages` の `syncScope`、6.2 は差分同期および `allowRedrive` を有効にしたページ・記録付き HTTP v2 で利用できる。受け入れ試験には固定された変更フィードとテスト受信先を使用した。[設定・CLI](../apps/server/README.md#incremental-sync)・[同期と再実行の試験](../apps/server/test/sync.test.mjs)・[プロセス強制停止試験](../apps/server/test/composition-crash.test.mjs)

- **6.1**　初回100件の後に作成2・更新3・削除1、重複2件と削除前の古い版を渡し、有効な変更6件、宛先101件、変更なしの回の送信0件を確認した。同じ通知キーは元の受付を返し、異なる起動が重なると次の run は同期位置の確定を待つ。照合待ちのオーナーと待機列は再起動をまたいで復旧する。受信側登録直後・応答前、最終バッチの位置確定直前・直後の計3地点で SIGKILL。各ケースで1,003件の内容と順序、次回の開始トークンを確認し、応答消失時の追加送信1回が元と同じキーであることを確認した。
- **6.2**　100件を25件ずつ渡し、57件目の成功後に認証情報の解決を失敗させた。閲覧履歴を削除し、子の新版を公開してから再実行しても元の版を使い、成功57件の追加送信は0件だった。通常ページ・差分ページ・単独の記録付き HTTP、途中ページの GET 失敗、非冪等送信の照合、受信先キーと復旧記録の期限切れ、明示取消を検証した。再実行受付コミット直後に SIGKILL して同じ失敗 ID で再要求した別試験では、受付済みの試行 ID を返し、100件が各1回だけ送信された。
- **適用条件**　差分ソースは業務 ID・単調な版・削除行・ラウンド完了トークンを返す。業務 ID ごとに削除を含む最大適用版を保持する。差分・再実行に対応するバッチの子は入力 → 記録付き HTTP → Return。通常の Phase 5 フローは従来どおり利用できる。失効トークンからの再同期は明示操作で行う。
- **回帰**　型検査、ビルド、単体183件、サーバー123件、ブラウザ80件に成功した。サーバー123件は Node.js 22.13.0 でも成功した。旧形式DBで受付済みの通常ページと重複通知、従来の待機・照合・取消・履歴再生を含む。

Phase 5 の main（7624479）と変更後を別 worktree、同一マシン・Node.js v26.13.0・pnpm 10.34.9 で各1回計測した。

| --- | ---: | ---: |

| 短い実行の受付 / キュー待ち / エンジン p95 | 1.02 / 1 / 1 ms | 1.02 / 2 / 1 ms |

### 独立レビューと再計測

再送の受付から資格情報の取得完了までに受信先のキーが失効するケースを追加した。ホストは実際の送信直前に期限を確認し、期限を過ぎた再送は照合待ちに戻す。取得件数には重複を含む元の行数を、集計には適用対象の行だけを使う。バッチ内でも直前の確定合計から入力順に加算する。410 は本文サイズによらず明示的な再同期の対象となる。以上の5点を修正前に再現し、修正後の成功を確認した。再実行が再度失敗した後に最初の要求が遅れて届く場合も、2回目の失敗 ID だけが次の試行を開始できた。

マージ対象の main（7624479）と修正後を別 worktree で再計測した。Node.js v26.13.0、pnpm 10.34.9、同一マシン。サイズと既存ベンチマークはそれぞれ1回、受注同期は5回の中央値。
