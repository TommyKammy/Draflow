# Phase 7 案　共有環境での実行と運用

対象は Phase 6 マージ後の main（f719639）。単一ホストで利用する組み込みエンジンとしては、固定版の公開、待機・再開、記録付き HTTP、子フロー、差分同期、並列バッチ、失敗位置からの再実行、順序付き補償まで揃った。共有サービスとして運用するときには、実行を引き継ぐ所有者、組織ごとの操作権限、外部結果が不明なときの運用者の判断経路が必要になる。[Phase 6 の実装と試験](phase6-plan.md)・[Node ホストの運用契約](../apps/server/README.md)

## 7.1　P0　台帳の契約と組織境界

SQLite の排他ロックを前提に、受付・実行・タイマー・復旧が一つのホストに集まっている。履歴ストアだけを差し替えても実行は引き継げない。まず、受付と通知の重複排除、子の作成と親の待機、外部操作の確定と進捗更新などを、まとめてコミットする台帳操作として定義する。SQLite を既定とし、共有用 PostgreSQL を選択可能にする。最初の移行時点で組織 ID を導入し、公開版、実行、資格情報の参照、通知キー、同期位置、照合・補償の所有組織を固定する。初版の PostgreSQL はワーカー1台で検証できる。[現行の台帳](../apps/server/src/sqlite.ts)

**受け入れ条件**

- 両台帳に同じ契約試験を適用する。受付直後、子の生成、外部登録の応答前、ページ位置の確定、補償子の完了で停止を注入し、親子関係、試行 ID、宛先の適用件数、照合対象が一致する。
- Phase 6 の DB に待機中・照合中・再実行可能な失敗・補償中の実行を用意する。受付を停止して指定組織に移行し、同じ通知・再実行・補償要求が元の受付を返す。移行中断後の再開で件数とキーが一致し、新台帳への受付開始前は旧 DB で再開できる。
- 2組織が同じフロー名、通知キー、業務 ID、資格情報名を使っても双方の実行が独立する。親子・復旧点・固定公開版を他組織のレコードに結び付ける書き込みを拒否する。同期位置や受信先キーの寿命も引き継ぐ。

## 7.2　P0　分散ワーカーと高可用性

受付、スケジュール発火、ジョブ実行を複数プロセスに分ける。DB 時刻による期限付き所有権と単調増加する世代番号を使い、チェックポイント・完了・子生成・次回発火の更新時に所有権を確認する。候補行の競合回避には PostgreSQL の行ロックが使える。DB 内の所有権だけでは送出済みの HTTP を取り消せないため、外部操作は Phase 6 の冪等キー・有効期限・手動照合を引き継ぐ。DB 自体の障害にはスタンバイと切替手順を用意する。[PostgreSQL の行ロック](https://www.postgresql.org/docs/current/sql-select.html)・[スタンバイと同期レプリケーション](https://www.postgresql.org/docs/current/warm-standby.html)

**受け入れ条件**

- 受付2台・ワーカー3台で同じ通知と同じスケジュール時刻を同時投入し、受付は各1件。1,003件・41バッチの途中で所有者を停止する。新所有者の引継ぎ後に旧所有者を復帰させ、古い世代からの完了・子生成・カーソル更新の成功は0件。冪等な宛先の ID・版・集計が逐次実行と一致する。
- 結果不明の非冪等送信、受信先キー期限切れ、子孫が配送中に中断した補償対象フローを引き継ぐ。自動再送・自動返金は0件。待機通知と期限切れ、取消と子完了、再実行と補償はそれぞれ競合させ、確定した遷移が1回であることを検証する。
- 複数ワーカーの合計で宛先ごとの並列上限と429待機を守る。組織別の実行枠も設け、大量同期中に別組織の短いジョブが完了する。実際に共有する宛先アカウントの制限は全組織合計でも守る。
- 可用性目標の初期案は、ワーカー喪失から60秒以内に引継ぎ、同期複製された DB の単一ノード障害から5分以内に受付再開、成功応答済み受付の欠落0件。DB 切断中は未確定の受付に成功を返さない。旧プライマリの復帰、受付ノードの停止、バックアップの別環境への復元も実地試験する。バックアップ復元時は外部副作用と突き合わせてから送信を再開する。

## 7.3　P0（複数組織への提供前）　認証・認可・監査

現在の署名付き Webhook、待機トークン、ノード・宛先別 HTTP 資格情報はそれぞれ用途が異なる。管理操作は信頼されたローカル CLI／ホスト API にある。ここに認証済みの管理 API を設け、組織所属と役割をサーバー側で判定する。閲覧者、運用者、公開担当、組織管理者を分け、照合・補償・資格情報管理を個別に許可できるようにする。PostgreSQL の行レベルセキュリティを併用する場合は、実際の接続ロールで分離を検証する。[現在の管理操作](../apps/server/src/cli.ts)・[PostgreSQL の行セキュリティ](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

**受け入れ条件**

- 2組織×各役割で、一覧・検索・詳細・履歴・公開・子呼出し・再開・取消・再実行・照合・補償・資格情報変更の許可表を自動試験する。別組織の既知 ID を直接指定しても情報開示・状態変更・外部送信は0件。同じ接続を再利用して組織を切り替えても前組織の結果を返さない。
- 組織別の Webhook 署名鍵、待機トークン、資格情報を相互利用できない。権限剥奪後の次の管理要求は拒否する。ワーカーやスケジューラも受付時の所有組織を引き継ぎ、他組織の秘密を解決できない。
- 照合・再実行・補償・公開・権限変更について、組織、実行者、対象、理由、時刻、結果を追跡できる。受付済みの状態変更と監査記録は同時に確定し、履歴削除後も監査できる。画面・API・ログ・監査に秘密値や待機トークンを出さない。

## 7.4　P1　運用者向け画面と監視

既存の編集・履歴再生に加え、全実行から対応が必要なものを見つける画面を作る。先に読み取り専用の一覧・詳細・通知を出し、7.3 の管理 API を通じて操作を追加する。初版の主要な利用場面は「配送結果が不明な注文を探し、受信先と照合し、必要な次の操作を一度だけ行う」とする。

**受け入れ条件**

- 組織、公開版、期間、状態で絞り込み、親から子、外部操作、再実行・補償の試行へ移動できる。通常の待機、429待機、照合待ち、中断、補償中、要手動対応を区別し、元の失敗と補償の結果を同時に確認できる。
- 受信先での適用を確認した運用者が、理由を記録して該当する操作を照合できる。2人が別タブから逆の判断を送信する試験では1件だけ確定し、他方には最新状態を示す。二重クリック・再読込で再送や返金が増えない。閲覧者には操作権限を与えず、キーボードだけでも一連の作業を完了できる。
- キューの最長待ち時間、最終ハートビート、照合待ちの最長時間、補償失敗の件数を取得できる。ワーカーを停止し、設定した閾値内に通知され、対象実行と復旧後の状態を画面からたどれる。10万件の履歴で一覧先頭ページの p95 1秒以内を初期目標とし、本文の一括読込を避ける。

## 出荷判断

7.1・7.2 を単一組織の HA 構成の出荷単位とし、複数組織の共同利用は7.3通過後、一般運用者への復旧操作の提供は7.4通過後とする。各段階で Phase 6 の SQLite 回帰、Node.js 最小サポート版、ブラウザ試験を継続する。Phase 6 main と同条件で受付・キュー待ち p95、同期完了時間、ピーク RSS、台帳サイズ、配布 gzip を記録する。DB ドライバーと運用者画面は任意導入にし、組み込みエディタの配布物に含めない。

汎用性の次の候補には、任意の分岐を同期する並列合流、実行中フローの公開版移行、履歴・補償データの保持／削除方針がある。共有運用ではデータ保持期限を先に決め、期限内の照合・復旧・監査に必要な記録を保護する。任意グラフの補償やマルチリージョン同時書込みは、業務上の順序と整合性要件が明らかな案件で別途設計する。上記の台数・時間・件数は試験条件または提案値であり、実測 SLA ではない。

## 7.1・7.2 実装後の検証（2026-11-27）

7.1 は組織ごとに PostgreSQL スキーマと接続先の組織を固定する方式を採用した。7.2 は短い台帳トランザクションを組織内で直列化し、外部 I/O の間はロックを解放する。組織をまたいで共有する上流アカウントの同時実行枠と待ち時間は別の共有テーブルで管理する。[起動・移行・復旧手順](../apps/server/README.md#shared-postgresql-ledger-and-worker-roles)

- **組織と移行**　同名フロー・同じ通知キー・同じ業務 ID と版・同名資格情報を2組織で利用し、実行、受信先キー、同期トークン、解決された資格情報の独立を確認した。SQLite からの移行中に書き込みを失敗させてロールバックし、元の台帳で待機を確認してから再移行した。待機、要照合、再実行、補償を検証した。Phase 6 のコミット `f719639` で実際に補償プロセスを強制終了して作成した DB も移行し、予約・請求・返金・予約解除が各1回になった。
- **ワーカーの引継ぎ**　受付2プロセスへの同時通知が同じ実行 ID を返し、一方の受付を終了しても他方が同じ ID を返した。受信先が最初の更新を適用した直後にワーカーを停止し、代替ワーカー2台を起動。3.120秒で同一キーの再送を受信した。旧ワーカーを復帰させ、1,003件・41バッチについて全 ID、版、集計と適用件数が一致した。旧世代による送出・完了・子生成・ページ更新は拒否された。スケジューラ2プロセスが同じ期限を処理しても受付は1件だった。
- **競合と配送**　待機通知と期限切れ、親取消と子完了の両順序、再実行受付と補償要求、受信先キー期限切れ、手動配送の結果不明、補償中の強制終了を検証した。別組織が同じ上流アカウントを使う場合の同時実行上限1と429待機、大量実行中に別組織の短いフローが完了することも確認した。
- **DB 障害**　Docker の PostgreSQL 18.4 同期スタンバイを使用。プライマリを停止して受付不能を確認し、スタンバイを昇格して0.709秒で同一の受付 ID 20件を確認した。旧プライマリは読み取り専用で再参加した。別 DB へのバックアップ復元でも20件すべての待機列と ID が一致した。計測に本番の障害検知・接続先配布時間は含まない。

| 指標 | Phase 6 | 7.1・7.2 |
| --- | ---: | ---: |
| 受付 p95 | 0.57 ms | 0.75 ms |
| キュー待ち p95 | 1 ms | 1 ms |
| 同期完了（逐次／並列4） | 3,140／992 ms | 3,283／1,005 ms |
| ピーク RSS（逐次／並列4） | 100,400／99,536 KiB | 100,304／98,992 KiB |

型検査とビルドに成功。Vitest 183件、サーバーの既定構成151件、ブラウザ80件が成功し、Node.js 22.13.0 でもサーバー151件が成功した。外部 DB を必要とする9件は既定構成でスキップし、PostgreSQL を指定した別実行で確認した。共有台帳・分散の契約試験は10件、既存の補償・強制終了・競合シナリオの共有台帳での実行は24件成功した。

## 7.1・7.2 独立レビュー

- 組織IDを両台帳で検証する。UTF-8変換で同じ値になる異なる文字列、空文字、NULを拒否し、組織の取り違えを防ぐ。
- PostgreSQLで期限切れの通知キーを再利用した際に受付順を更新する。同一キーのWebhookを間に挟んでも、送信元を省略した照会が最新の受付を返す。
- 発火前の再登録で次回時刻が同じ場合も、期限とスケジュール定義の双方を確認して古いスケジューラによる更新を拒否する。
- 受付専用プロセスもDB接続断を検知して異常終了する。Docker上の同期プライマリをSIGKILLし、待機中の受付が追加要求なしで終了、昇格後の照会まで0.916秒、成功応答済み20件の欠落0件を確認。旧プライマリは読み取り専用で再参加し、別DBへのバックアップ復元で20件が一致した。
- 受付2台・ワーカー3台の試験で、受信先への適用後に旧所有者を停止。3.136秒で代替ワーカーから同じキーを受信した。旧所有者の復帰後も1,003件・41バッチのID・版・集計が一致した。手動配送と期限切れキーは照合に回る。
- Phase 6 のコミット `f719639` で補償を中断したSQLiteを2回インポートし、件数と指紋が一致。再開後の予約・請求・返金・予約解除は各1回。誤った組織への移行、取込後に変更された元DBの再取込も回帰試験に含めた。

### レビュー時の再計測

同一マシン・Node.js 26.13.0で `f719639` と比較。SQLiteの同期時間・最大RSS・DBサイズは1,003件、逐次／並列4の各5回の中央値。p95は既存の受付ベンチマーク1回の測定値。

| 指標 | Phase 6 main | レビュー後 |
| --- | ---: | ---: |
| SQLite受付／キュー待ち p95 | 0.92／1.00 ms | 0.74／1.00 ms |
| SQLite同期完了（逐次／並列4） | 3,332／999 ms | 3,190／999 ms |
| ピークRSS（逐次／並列4） | 100,480／99,792 KiB | 100,224／99,232 KiB |
| SQLiteファイル（逐次／並列4） | 1,290,240／1,314,816 B | 1,298,432／1,318,912 B |
| サーバーJS合計（生／ファイル別gzip） | 135,200／33,207 B | 166,723／42,902 B |
| エディタ要素／デモJS（gzip） | 38.5／68.4 KB | 38.5／68.4 KB |

サーバーJSは `apps/server/dist/*.js` の合計で、ドライバーなどの外部依存を除く。PostgreSQL 18.4の共有台帳も同じ1,003件を単一ホスト・並列4で計測した。参考値（1回）は20.04秒、同時に投入した短いジョブの受付p95は3.42 ms、キュー待ちp95は276 msだった。共有モードでは同期的な台帳操作がDB往復を伴う。再現には使い捨てDBを指定し、`DRAFLOW_BENCH_POSTGRES` を設定して `node apps/server/test/parallel-bench.mjs 4` を実行する。
