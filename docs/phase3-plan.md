# Phase 3 提案　短時間のワークフローを無人運転する

評価対象は PR #17 マージ後の `main`（`f0447eb`）。Phase 2.5 までで、ホストが起動した JSON アイテムのフローを実行し、利用者が作成・検証・調査するところまで揃った。次の到達点は「エディタを閉じても、公開した版が外部イベントまたは時刻で起動し、再起動後も受付と結果を照合できる」。単一ホスト・単一ワーカーを初版の前提とする。数日間の承認待ちや複数ホストでの継続実行には別の実行契約が必要になる。[原設計の Phase 3](design/draflow-design.md)・[Phase 2.5 の完了条件](phase2.5-plan.md)

今回のローカル確認では型チェック・単体156件・本番ビルドが成功した。gzip は core＋nodes 47.2 KB（ファイル個別の gzip 合計）、element 36.0 KB、デモ 63.1 KB。PR #17 の CI は test・browser ともに成功している。[検証済みの PR](https://github.com/TommyKammy/Draflow/pull/17)

## 現状の判定

| やりたいこと | 現状と根拠 | 判断 |
| --- | --- | --- |
| アプリの操作から HTTP → 変換 → 分岐・合流を実行 | 7標準ノード。If／Filter、同一ポートへの合流、複数入力 Merge、アイテムの由来、個別の実行回を扱う。実行回数・件数・時間の上限とキャンセルもある。[標準ノード](../packages/nodes/src/index.ts)・[エンジンの回帰テスト](../packages/core/test/engine.test.ts) | **十分**。短時間の処理を埋め込む用途でコアの全面改修は不要。 |
| ホスト独自の業務処理を追加 | バージョン付きノード、パラメーター定義、式、資格情報取得、時計・fetch の注入点がある。レジストリには要求版がない場合に下位版を選ぶ動作もある。[SDK](../packages/core/src/node.ts)・[レジストリ](../packages/core/src/registry.ts) | **十分**。本番公開時には実際に解決した実装版を記録する。 |
| 作成・調査・再編集 | 部分実行、ピン、式補完、記録した入出力の閲覧とコピーが可能。メモリ履歴は任意で、有効にしたホストだけが負担する。[埋め込み手順](embedding.md) | **十分**。サーバー実行からも同じ履歴形式を供給する。 |
| API の配列を明細ごとに処理して再集計 | HTTP はトップレベルの JSON 配列を1アイテムの `data` に格納する。Filter は流れてきたアイテムを判定する。式で配列を加工できても、その結果を独立した複数アイテムに展開する標準ノードはない。[HTTP](../packages/nodes/src/http.ts)・[Filter](../packages/nodes/src/filter.ts) | **一部不足**。Split Out の優先度が高い。逆方向の Aggregate は複数起源の扱いも決める。 |
| ブラウザを閉じて受信・定期実行 | SDK に `trigger`／`webhook` があり、エンジンに開始ノードと入力を渡せる。配布構成には常駐 runtime、ルート登録、スケジューラがない。[SDK](../packages/core/src/node.ts)・[起動処理](../packages/core/src/engine.ts) | **不足**。Phase 3 の主目的。 |
| 下書きの編集、公開版の実行、再起動後の受付復元 | WorkflowStore は文書の load/save。ExecutionStore は終了した実行のサマリーと詳細。受付済みイベント、公開版、実行中の所有状態を原子的に保存する契約はない。[文書ストア](../packages/storage/src/index.ts)・[履歴ストア](../packages/storage/src/executions.ts)・[記録処理](../packages/element/src/record-execution.ts) | **不足**。受付台帳と閲覧履歴は保持期間も責務も異なる。 |
| 外部 API の認証、失敗時の再試行 | コアに CredentialProvider とノード単位の retry がある。標準 HTTP はヘッダーを受け取る。再試行はノードの execute をやり直すため、複数アイテムの後半で失敗すると先に成功した送信も繰り返し得る。[実行処理](../packages/core/src/engine.ts)・[HTTP](../packages/nodes/src/http.ts) | **一部不足**。サーバー側の参照解決と副作用の重複方針が必要。 |
| 翌日の承認から同じ実行を再開 | `waiting` 型や合流待ちがあっても、実行スタック、未充足の入力、次の runIndex、由来情報は実行中のメモリにある。P7 のリプレイは保存済みタスクを読む。[エンジン](../packages/core/src/engine.ts)・[リプレイ](../packages/element/src/execution-replay.ts) | **不足、別段階**。履歴は容量超過で詳細が省略されるため復旧の正本にはできない。 |

例えば、申請フォームの入力を直ちに検証して振り分ける処理は現状でも組み込める。夜間に受注明細を同期する処理には定時起動・明細展開・認証・重複対策が加わる。担当者が翌日承認するまで止める処理には、さらに永続的な待機と再開が加わる。この順で用途を広げる。n8n でも外部リクエストを受ける Webhook と、状態をデータベースに退避して後で継続する Wait は異なる機構として提供されている。[Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/)・[Wait](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait/)

## 推奨する実装順と受け入れ条件

| 順序 | 実装範囲 | 合流判定 |
| --- | --- | --- |
| R1　公開版と起動契約 | 任意の `@draflow/runtime`。まずメモリ実装で下書き、検証済み公開版、稼働中の版を区別する。既存エンジンに開始ノード・入力・実行 ID を渡し、発火元、文書 ID、公開版、実際のノード版を記録する。 | トリガーが2個ある図で発火した側だけが走る。公開後に下書きを変えても結果は旧版のまま。登録途中の失敗で旧版が稼働し続け、activate/deactivate の反復で登録が増えない。復元先で実装版が違えば受付を開始する前に理由を返す。 |
| R2　永続受付と Node ホスト | `apps/server` と Node 専用 SQLite アダプター。公開版、発火キー、run ID、待ち行列、実行状態を保存する。受付とキュー投入は同一トランザクション。実行履歴は P6 形式を利用し、P7 から読めるようにする。初版は同時実行1、キュー長に上限を置く。 | プロセス終了を受付前・受付直後・実行中・終了確定後に挿入して再起動する。受理済み未開始は復元し、完了済みは走らない。実行中だったものは「中断・要確認」として残し、自動再送しない。同じ発火キーの同時受付で作る run ID は1つ。満杯・書き込み失敗時は受理成功を返さない。 |
| R3　資格情報と HTTP | サーバーだけが資格情報 ID を許可された provider に渡し、標準 HTTP が認証スロットを利用できるようにする。まずホスト提供の API キー／Bearer を扱う。履歴に保存する本文・エラーの扱いと上限も決める。 | ダミーの秘密値でモック API が成功する。エクスポート文書、ブラウザ、実行ログ・エラー、保存履歴に認証値が出ないことを失敗応答も含めて確認する。未許可・参照切れは送信前に失敗する。大きな応答はホストのバイト上限で停止する。 |
| R4　Webhook | テスト用の一時受付と公開版の本番受付を分離。最初は永続受付後に ID と 202 を返す非同期応答。認証・署名検証はホストの入口で行い、検証後のペイロードだけをワークフローに渡す。 | 無効な署名・本文上限超過・経路競合では実行0件。再配信された同じイベントは同じ run ID を返す。未公開・無効化済みの本番 URL は起動しない。テスト受付の期限切れ後に本番へ処理が漏れない。 |
| R5　スケジュール | interval を先行し、次に仕様を限定した5フィールド cron と明示タイムゾーン。予定時刻を発火キーにする。初版の停止中取りこぼしは直近1回まで補完し、古い全件を一斉起動しない案とする。 | 偽時計で通常境界・停止中の複数周期・再起動・無効化を検証する。DST で存在しない現地時刻はスキップ、二度現れる同じ指定時刻は1回とする。再起動をまたいでも同じ予定を重ねて受理しない。 |
| R6　実務フローでの仕上げ | 独立して実装可能な標準 Split Out と Aggregate を追加。既存ポート・pairedItem の契約を使い、複数起源の集約では単一祖先への参照が曖昧な場合の操作を明示する。 | mock API の受注明細配列 → 展開 → Filter → 集計 → 送信を、同じ公開版の Webhook と定時起動で通す。空配列、複数入力、同名キー、由来と数値型を確認する。再配信・再起動・履歴の再表示で意図しない追加送信がないことを呼び出し回数で確認する。 |

R1–R4 で最初の本番ユースケース「認証付き Webhook → 外部 API」が成立する。最終ノードの値を HTTP 応答に返す同期モードと専用応答ノードは、同期 API の需要が出た時にタイムアウト・切断・二重応答を含めて追加する。R5 は定期処理、R6 は標準ノードだけで完結する業務例の完了点。元設計の1〜2週間は Webhook／cron を動かす範囲の目安であり、永続受付や停止点の障害試験を含む見積もりには使わない。

### 保証する範囲

- **重複**。送信元のイベント ID と受付元を組み合わせて重複を検出し、その有効期間を設定する。ID がない別々の HTTP リクエストを本文一致だけで同一視しない。外部 POST 成功直後にプロセスが落ちた場合、ローカル台帳だけでは外部成功を証明できない。相手が対応する場合は同じ冪等キーを渡し、それ以外は中断状態から人が照合する。
- **版と保持期間**。受理した実行はその時点の公開版に固定する。公開差し替えは新規受付に適用し、待ち行列が参照する版は保持する。大きな履歴詳細を削除しても受付の重複判定は独立して働く。中断を P6/P7 でどう表示するかは R2 で既存履歴との互換テストを付けて決定する。
- **配布と性能**。既存4パッケージのブラウザ入口にサーバー・SQLite・スケジューラを取り込まない。Node のサポート下限で保存アダプターを CI 実行する。各 PR で型・単体・ブラウザ・gzip・キャンバス・式の既存ゲートを維持する。サーバー側は受付から応答までと、キュー待ち・エンジン実行を別々に計測し、R2 の実測で性能予算を決める。[既存の計測条件](phase2.5-plan.md#各-pr-の合流条件)
- **運用の最小単位**。文書 ID・公開版・発火キー・run ID で受付から結果を引けるようにする。キュー件数、最古の待ち時間、失敗・中断件数を確認でき、停止時は新規受付を閉じて実行中を期限付きで待つ。管理操作は最初は信頼されたホスト／ローカル CLI に置く。

## 次の段階に回す機能と判断基準

| 候補 | 昇格させる条件 |
| --- | --- |
| 永続 Wait／承認・再開 | 最初の用途が承認・コールバック待ちなら R6 より優先する。継続状態の版、合流待ち・由来・タイマーの保存、再開トークンの一度限りの消費、再開と取消の競合を独立したマイルストーンで扱う。 |
| サブワークフロー | 複数フローで同じ業務処理を共有する要求が生じたら、親子 run ID、呼び出し先の版、入出力、再帰上限、取消伝播をまとめて設計する。 |
| ポーリング、ページング、バッチ・並列処理 | 受信 Webhook を持たない API や多数ページの処理が最初の接続先なら優先する。カーソルの永続化、部分成功、レート制限を実データで検証する。独立枝の並列化は合流順・由来・メモリの計測後に判断する。 |
| 永続バイナリ、OAuth 更新、コネクター群 | 現状の BinaryRef や資格情報参照を活かす。ファイル転送や OAuth 必須サービスが具体化した時に、保存期限・失効・更新競合を扱う。 |
| 分散ワーカー、テナント分離、任意コード実行 | 単一プロセスの容量・可用性が要求を満たせない場合、または信頼境界の異なる利用者に提供する場合に再設計する。初版の信頼された自作ノードの登録とは要件が異なる。 |

**着手提案**。まず R1 を、既存のエンジンを公開版と発火元に結び付ける小さい PR として進める。最初に運用したいフローが短時間の API 連携である限り、R2 の再起動試験を通してから外部イベントの入口を公開する。
