# Phase 4 提案　待機を含む業務フローを同じ実行として完了する

2026-11-27 時点の main（`21878e0`）を評価した。Phase 3 は単一ホストで短時間の API 連携を無人運転する用途には十分である。Phase 4 では「申請を受け付け、翌日に承認結果を受け取り、元の公開版の続きを実行する」までを推奨する。原設計の Phase 4「操作感の仕上げ」は初期ロードマップの名称で、部分実行・リプレイ・式補完などは既に実装されている。本案は Phase 3 完了後のエンジン拡張として扱う。[原設計](design/draflow-design.md)・[Phase 3 の繰り越し候補](phase3-plan.md)

## 用途別の評価

| 用途 | 判定 | 実装上の境界 |
| --- | --- | --- |
| アプリに埋め込んで入力を変換・判定する | 十分 | 式、If／Filter、Merge、アイテムの由来、版付きカスタムノードがある。部分実行・ピン・入出力履歴で動作を調べられる。[標準ノード](../packages/nodes/src/index.ts)・[組み込みガイド](embedding.md) |
| Webhook または定時起動で受注明細を同期する | 十分 | 公開版への固定、SQLite 受付、イベント ID による重複検出、サーバー側の認証付き HTTP、明細展開・集計が揃う。Webhook は受付後に 202 と run ID を返す。件数・時間が既存の上限に収まる処理が対象。[受注同期例](../examples/order-sync.json)・[Webhook 試験](../apps/server/test/webhook.test.mjs) |
| 障害後に安全に続きを実行する | 部分対応 | 未着手の受付は回収できる。実行中の停止は interrupted として記録する。ノードの retry とエラー出力はあるが、HTTP が複数件の途中で失敗すれば、それ以前に成功した送信も再試行の対象になる。[台帳](../apps/server/src/sqlite.ts)・[エンジン](../packages/core/src/engine.ts)・[HTTP](../packages/nodes/src/http.ts) |
| 翌日の承認、締切、外部ジョブ完了を待つ | 不足 | Schedule は新しい実行を起動する。実行中のキュー、未充足の合流、実行回と由来をまたいで再開する仕組みはない。履歴リプレイは調査用で、保持・省略の対象になる。[実行ループ](../packages/core/src/engine.ts)・[履歴リプレイ](../packages/element/src/execution-replay.ts) |
| 複数ページの取り込み、業務処理の共有 | 部分対応 | ホスト独自ノードで実装できる。途中から取り直せるカーソル・バッチ境界や、版を固定した親子ワークフローの呼び出しは標準機能として未整備。[SDK](../packages/core/src/node.ts)・[標準ノード一覧](../packages/nodes/src/index.ts) |

## 実装順と合格条件

| 順序 | 実装する範囲 | 受け入れ試験 |
| --- | --- | --- |
| 4.1 継続状態の保存 | 明示した待機点で、公開版・ノード実装版、次の実行位置、未処理の枝、合流入力、実行回、式が参照する結果と由来を保存する。待機登録と保存を SQLite の同一トランザクションに含め、ワーカーを解放する。形式に版を持たせる。 | 分岐の片側を待機させ、もう片側の入力を保持する。待機中に別の実行を完了し、公開差し替え・再起動・閲覧履歴削除後に、元の版で合流順・式の値・由来が連続実行と一致する。旧 DB の queued／interrupted も移行できる。 |
| 4.2 時刻・イベントによる再開 | Wait に指定時刻と外部イベントの二方式を設ける。再開データの形式、待機期限、取消、再開の認可を定義する。待機ごとの識別子の消費と実行キューへの復帰を原子的に行う。待機期限と CPU・HTTP を含む実行中のタイムアウトを区別する。 | 停止中に期限が到来しても復帰は一度。再送、期限切れ、取消との同時到着、別実行宛ての通知を試し、有効な状態遷移だけが一度成立する。 |
| 4.3 外部送信の部分成功と運用 | HTTP の論理操作ごとに安定した冪等キーと未送信・成功・結果不明を記録する。キーは同じ実行内の別の反復や明細と区別する。相手が冪等キーを受理できる場合の再試行と、結果不明時の手動照合を用意する。CLI／履歴で待機理由、期限、照合対象、操作結果を追えるようにする。 | 3件中2件目の送信前、送信成功直後、結果保存直後にそれぞれ強制停止する。確定済みの1件目は再送されず、結果不明の2件目は接続先の契約に従って同じキーで再試行するか照合待ちになる。 |
| 4.4 業務例を通す | 申請 → 承認待ち → 承認なら外部登録、却下・期限切れなら各経路で終了。担当者の認証と承認画面はホストが提供し、Draflow は判断結果と実行を結び付ける。 | 待機中に再起動・再公開し、旧版の申請を承認、新版の申請を却下する。二重クリックでも旧版の登録は1件、新版は0件。期限切れと取消も履歴から説明できる。 |

初版の保証は明示した待機点からの再開と、記録対象とした HTTP 操作の復旧に限定する。任意のカスタムノードの途中で停止した場合は現行の interrupted を維持する。待機データには容量・有効期限・削除条件を設け、参照中の公開版を保持する。SQLite・タイマー・受信 API はサーバー側に置き、既存のブラウザ実行と JSON ワークフローの互換性を型・単体・ブラウザ試験と gzip 計測で確認する。

## 実装・検証結果（2026-11-27）

- **4.1**　待機中に別の受付を処理し、公開版の差し替え・履歴削除・再起動後の結果を、待機を挟まない対照実行と比較した。旧スキーマの queued と interrupted を維持する移行も確認した。[継続状態の試験](../apps/server/test/continuation.test.mjs)
- **4.2**　時刻待機、期限付きイベント、取消を実装した。停止中に到来した時刻と期限を回収し、別実行のトークン・消費済みトークンで後続処理が動かないことを確認した。[ホスト操作とコールバック](../apps/server/README.md#durable-waits-and-recorded-http)
- **4.3**　HTTP v2 で記録対象を選べる。未送信・結果不明・成功を明細別に追跡する。送信前・相手側成功直後・結果保存直後に子プロセスを強制停止し、冪等キー方式と手動照合方式の計6ケースで、各明細の適用が1回になることを確認した。[強制停止試験](../apps/server/test/journal.test.mjs)
- **4.4**　署名付き Webhook で申請を受け、単回トークンで承認する例を追加した。再公開後に旧申請を二重承認し、新申請の却下・期限切れ・取消を含めても、外部登録は旧版の宛先への1件となった。登録先にはテスト用の受信処理を使用した。[申請ワークフロー](../examples/approval.json)・[業務例の試験](../apps/server/test/continuation.test.mjs)

## 優先順位を変える条件

- 最初の案件が大量同期なら、4.2 の承認向けイベントよりページング・カーソル保存・部分再試行・429 の待ち時間を先に扱う。合格条件は途中ページの失敗後に欠落・二重登録なく完走すること。
- 同じ業務処理を複数の公開フローで共用する案件が出たら、サブワークフローを次候補とする。親子 run ID、子の公開版固定、入出力、取消・失敗伝播、再帰上限を一緒に設計する。
- 同期 Webhook 応答、OAuth 更新、永続ファイルは必要な接続先が決まった時点で評価する。分散ワーカーは単一ワーカーのキュー待ち・可用性要件を測って判断する。担当者一覧・代理承認などを共通製品化する場合は、ホストとの権限分担を別途決める。

比較基準として、n8n の Wait は保存した実行を時刻や Webhook で再開する。AWS Step Functions も外部ジョブ完了や人の判断を待つコールバックを、通常のサービス呼び出しと区別している。この二つは、Draflow の新規受付と同一実行の再開を区別する参考になる。[n8n Wait](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait/)・[AWS Step Functions の連携パターン](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)
