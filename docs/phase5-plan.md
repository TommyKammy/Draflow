# Phase 5 提案　公開フローの再利用と、途中から続けられる大量同期

2026-11-27、Phase 4 マージ後の main（`3570fc8`）を評価した。既存の受注同期と承認を題材に、単一ホスト・単一ワーカー・軽量なブラウザ埋め込みを前提とする。原設計の「Phase 5: 埋め込みと配布」は別のロードマップ項目として追跡する。本提案はエンジンの次期機能に関するもの。[原設計](design/draflow-design.md)・[Phase 4 の計画と検証](phase4-plan.md)

## 推奨する順序と受け入れ条件

### 5.1　P0　公開サブワークフローを呼び、結果を親に返す

2つの親から共通の「明細検証・登録」を呼べるところまでを最初のリリース単位にする。親の公開時に、許可された子の ID・公開版・呼び出し用入口を固定する。最初は入力アイテム列を一括で渡し、明示した戻り口から順序付きアイテム列を返す。親から参照できるのは子の戻り値。子の内部ノードの詳細は子 run の履歴を開いて調べる。

- 親の待機登録、呼び出し位置（親 run・ノード・実行回）、子 run の受付を同一トランザクションで確定する。子の完了と親の復帰も一度だけ確定する。唯一のワーカーを親の同期呼び出しで占有しない。
- **受け入れ**　2つの親が同じ子 v1 を使用する。子が承認待ちの間に無関係のジョブが完了する。子 v2 を公開して再起動しても既存の親は v1 を使い、v2 を指定して再公開した親だけが新しい結果を受け取る。空入力・空出力・複数行で順序と対応元を検証する。
- **障害・権限**　子受付と親復帰の各コミット前後で強制停止し、子 run 数・親の後続実行・外部登録が各論理呼び出しにつき1回であることを記録対応のテスト受信先で確認する。子のエラーは親の stop／continue／errorOutput に従う。子が照合待ちなら親も結果を待つ。親取消と子完了が競合しても終端は一つとし、既に外部へ送った結果は照合できるよう残す。
- **公開・運用**　呼び出し許可のない子、存在しない版、直接・間接再帰、設定深度超過は子受付前に拒否する。子の HTTP は子の資格情報許可だけで動く。親子 run・呼び出し位置・双方の公開版を相互に引ける。履歴詳細を削除しても待機中の親に結果が一度だけ届く。

### 5.2　P0　ページ取得と逐次バッチを、同じ同期として復旧する

ページは外部 API の読み取り単位、バッチは下流への引き渡し・部分成功の確定単位である。ページサイズ100、送信先上限25なら、1ページから最大4バッチが生じる。初版は GET の固定エンドポイント＋不透明カーソル、同時実行1、入力順処理を推奨する。大きな配列全体を出力せず、5.1 の子に各バッチを引き渡し、親には件数・集計値・失敗位置を返す。

- 現在ページのデータと次カーソル候補を保存し、論理バッチに安定した ID を与える。子の結果確定と進捗を結び付け、全バッチの成功後に次カーソルを確定する。完了ページの明細を復旧用チェックポイントから解放する。通常のノード出力の由来・履歴契約は維持する。
- **受け入れ**　固定された1,003件を100件ずつ読み、25件ずつ渡す。11ページ、41バッチ、末尾3件で、受信 ID の集合・順序・集計値が元データと一致する。7ページ目の途中と、最終バッチ成功後のカーソル確定前に強制停止する。確定済みページを読み直さず、確定済みの登録も繰り返さない。結果不明の送信は Phase 4 と同じ方式で再試行または照合する。
- **境界**　次カーソルがある空ページは続行し、終端カーソルで完了する。反復カーソル、失効カーソル、ページ数・件数・バイト数の上限超過は理由と最後の確定位置を残して停止する。失効時に無断で先頭からやり直さない。任意の next URL、offset、並列実行は対象 API を決めてから広げる。
- **容量と保証範囲**　全体で 8 MiB を超える固定データを、各 HTTP 応答 1 MiB 未満で処理し、チェックポイントの最大バイト数とピークメモリを計測する。10倍のページ数でも復旧に必要な明細は現在ページ・進行中バッチの範囲に収まり、既存の 8 MiB 上限内で完走する。監査記録の総量は別に測る。一貫したスナップショットを提供しない API では取得中の更新による欠落まで保証できない。実行をまたぐ増分同期には安定した業務 ID と更新位置の契約が別途必要になる。

### 5.3　P1　レート制限・取消・進捗照会を含めて運用できるようにする

- **待機と再試行**　読み取りの 429／一時的な 503 では Retry-After の秒数・HTTP 日付を解釈し、再試行可能時刻を SQLite に保存する。値がない、または不正なら上限付きバックオフを使う。最大試行回数・総期限を持ち、401／403 は設定修正が必要な失敗として記録する。書き込みの再試行は Phase 4 の送信契約に従う。[Retry-After の仕様](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)
- **受け入れ**　偽時計で「7ページ目が429 → 待機中に再起動 → 指定時刻に成功」を通す。期限前の追加送信は0回で、待機中に別ジョブが完了する。バックオフがなくても、進行中の同期がバッチ境界でワーカーを譲り、後から受け付けた短いジョブが同期の完了前に終了する。
- **診断と取消**　親子 run、確定ページ、完了バッチ・明細数、照合対象、次回試行時刻を CLI と履歴から追える。待機中に取り消してから再起動しても新しいページ取得・外部送信は0件とし、既に成功した分と照合が必要な分を表示する。生のカーソルや資格情報は閲覧履歴に出さない。

## Phase 5 の出荷判定

5.1 は単独で出荷可能。5.2 と 5.3 は「定時起動で受注を同期し、失敗時に担当者が続きから復旧できる」一つの業務例でまとめて判定する。PR ごとに旧 SQLite の queued／waiting／review／interrupted を引き継ぎ、既存の Wait、二重通知、記録付き HTTP、部分実行、履歴再生を回帰試験する。最小サポート版 Node とブラウザで検証し、main と同条件で gzip、短いフローの受付 p95、式・キャンバスの性能を比較する。サブワークフローとページ処理の永続化は Node ホスト側に置く。

最初の案件が一つの大規模同期で、共用する子フローが決まっていなければ、5.2 のカーソル保存と固定バッチ処理を先に縦に通す。5.1 の汎用呼び出し UI をその前提にしない。初版の導入順を決める材料は、共用したい実フローの数、接続先のカーソル仕様、1日の件数、送信先の冪等性である。

| 残る候補 | 優先度を上げる条件 |
| --- | --- |
| 実行をまたぐ増分ポーリング、重複排除 | Webhook のない更新フィードを継続購読する。削除・遅延到着・同一時刻の更新を含む watermark の仕様が得られる |
| 並列バッチ、分散ワーカー、HA | 単一ワーカーでキュー待ち・完了時間の目標を超える、またはホスト停止を許容できない。並列度・順序・リース失効を測る |
| 補償処理・手動再実行 | 複数サービスへの登録後に業務上の取消が必要。各サービスの取消 API と補償自体の部分失敗を定義できる |
| OAuth 更新、永続バイナリ、同期 Webhook 応答 | 最初の連携先が更新トークン、ファイル転送、または同期応答を必須とする |
| テナント分離、承認者管理、標準の運用画面 | 複数組織への提供や担当者割当を製品側が引き受ける。現行の信頼済みホストとの責務を再定義する |
